# inframe

Try it in your browser: https://inframe.pages.dev (the video never leaves your browser).

Video in, clips out: the stretches of a video where the target is in frame. v0 finds "any person" (detect mode, the default) or "anything moving" (motion mode), stream-copies each stretch to its own file, and writes `segments.json` plus a LosslessCut CSV. No LLM anywhere: ffmpeg, NumPy / SciPy and a small open-weights detector (RF-DETR, Apache-2.0).

## Install

Needs macOS on Apple Silicon, `ffmpeg` and `ffprobe` on the PATH, and [uv](https://docs.astral.sh/uv/).

```
uv sync
```

Detect mode runs RF-DETR as CoreML packages (fp16, batch 8; compute units `CPU_AND_GPU` by default: about 11 ms per frame, 3x faster than `CPU_ONLY`, and repeatable because `bench/detect/export_gpu.py` (run by `setup.sh`) exports the small package with its topk in fp32; `INFRAME_DETECT_UNITS=CPU_ONLY` is the slower option that reproduces the reference run exactly, `CPU_AND_NE` is deterministic too but moves some interval boundaries of that run by 0.4-1.0 s. With an older package whose topk is fp16, inframe warns that it is stale and names the re-export command, because its GPU scores then change from run to run). They are exported once by `bench/detect/setup.sh` into `bench/detect/out/models/`. Point `INFRAME_MODELS` at another folder to use them elsewhere. If CoreML fails to load, or its predict() fails in the middle of a run, the run falls back to torch MPS (`uv sync --extra torch`) and says so loudly in the log and in `segments.json`. If the fallback is not installed, the samples scored so far are saved in `samples.csv`, `segments.json` gets an `error`, and the command exits with code 1 and a one-line message.

## Two modes

```
# 1. `--mode detect` (the default): any camera, RF-DETR person detector
uv run inframe cut VIDEO.mov --out OUT/detect

# 2. `--mode motion`: static camera, no model
uv run inframe cut VIDEO.mov --mode motion --out OUT/motion

# Optional: how much do the two agree?
uv run inframe compare OUT/motion/segments.json OUT/detect/segments.json   # writes OUT/compare.json and OUT/compare.md
uv run inframe compare A/segments.json B/segments.json --out DIR            # or into a folder you choose
```

`compare` refuses two runs of different videos (file name, size, fps or duration differ) with exit code 2. Without `--out` it writes into the parent folder of A's folder, which is `<stem>_inframe/` for the default layout.

Options (a negative `--pad`, `--min-len` or `--merge-gap`, `--fps` of 0 or less, or `--exit` above `--enter` is refused with a one-line message and exit code 2): `--preset fast|balanced|accurate` (fast = RF-DETR nano on keyframes only / motion at 2 fps; balanced = RF-DETR small at 5 fps; accurate = RF-DETR base at 5 fps: finds smaller people, costs more detector time; `inframe pick --preset accurate` and the MCP `cut_video(preset="accurate")` take it too; its CoreML package is `base_coreml_b1`, a batch of one, which the detector chunks to), `--fps N` (more than 0; the fast preset uses keyframes only), `--pad 1.0` seconds before and after, `--min-len 1.0`, `--merge-gap 1.5`, `--enter X --exit Y` (score thresholds; motion picks them from the video's own scores when you leave them out), `--min-box` (detect: ignore persons shorter than this fraction of frame height).

Output folder (default `<stem>_inframe/<mode>` next to the video, so the two modes never mix; a folder reused by a later run is cleared of the earlier run's clips): `<stem>_NN_<mmss>-<mmss>.mov` per clip, `segments.json` (source facts, mode, settings, score summary, unpadded `presence_intervals`, `clips` with start, end, file, peak score and sidecar name), `<stem>_losslesscut.csv`, `samples.csv` (score per sample), and one `<clip stem>.inframe.json` sidecar per clip (next section).

How it works: PyAV samples frames by timestamp in our code (software decode for H.264, VideoToolbox for HEVC / 10-bit, rotation applied by us). Per-sample scores go through hysteresis (enter / exit), gap merge, minimum length and padding. Cuts are `ffmpeg -ss ... -i ... -c copy`: lossless, audio and rotation kept, slow motion plays as filmed. A clip starts at the keyframe at or before the requested start, so it begins up to one keyframe interval early, never late. iPhone video is open-GOP: the pictures after a keyframe in decode order can show before it and cannot be decoded without the previous GOP. A second stream-copy pass starts audio and video together at the keyframe (the first video and audio packets are within one audio frame, 23 ms), still without re-encoding. Container metadata is dropped from clips, so location tags do not travel with them.

Motion mode: grayscale 320 px samples, background = per-pixel median of the first 10 s that then follows the light slowly, updated on background pixels only (a subject who stands still stays foreground; a pixel foreground for 5 minutes becomes background), score = foreground area fraction after a morphological opening, thresholds = median + 6 / 3 x spread of the scores (spread = 1.4826 x MAD, at least 2e-4; when the subject is in frame most of the time the thresholds come from the quiet samples instead). It estimates global camera shift against the background and warns when the camera is not static. A video that opens with the subject standing still gets a ghost there until the pixels are absorbed.

## Clip sidecar (`<clip stem>.inframe.json`)

Every clip gets a JSON sidecar next to it, e.g. `IMG_0001_01_0018-0036.inframe.json`, for downstream readers such as an editor script or an analysis tool. The schema is `docs/sidecar.schema.json` (JSON Schema 2020-12, `schema_version` "1.2"; a reader refuses another major version and ignores unknown fields). It holds:
- `source`: path and SHA-256 of the whole source file (computed once per run), and its duration.
- `clip`: file, `in_source_s` / `out_source_s` (the padded stretch), `copy_start_s`, where the stream copy really starts (measured on the cut: usually the keyframe at or before `in_source_s`, one GOP earlier when ffmpeg's mov demuxer will not seek to a keyframe for a request within two frames after it, as in iPhone HEVC), and `duration_s`, the clip file's video duration as written (ffprobe).
- `try_number` (1-based, time order) and `tries_total`.
- `video`: fps, `rotation`, `mirrored`, stored and display size.
- `time_base`, `coordinate_frame`: `source_time` is the file's own timeline in seconds (what `ffmpeg -ss` counts), slow motion not divided out; `clip_time = source_time - copy_start_s`, also in a clip retimed with `--slowmo` (its optional `slowmo` block, added in 1.2, says a player then shows `clip_time * factor` seconds). Boxes are `[x0, y0, x1, y1]` normalised to the upright display frame (display matrix applied: rotation, then any mirror), origin top-left, y down; multiply by `display_width` / `display_height` for pixels. A reader that wants pixels multiplies by the display size; for real seconds it multiplies file time by the clip's time scale (1/slowmo factor for baked slow motion).
- `target.name`, `embedder` (null for `any-person` and motion mode), `detector` (mode, backend, model, tracker), `sampling`.
- `presence_in_clip`: the unpadded in-frame stretches cut to this clip, in source and clip time.
- `samples`: one entry per scored sample from `copy_start_s` to the end: `source_time`, `clip_time`, `box` (null when there was none), `confidence` (the target's score, 0 = not in frame; detect: the detector's 0..1 score, motion: the share of the frame that moved, so read it against the top-level `score` object with `kind`, `enter` and `exit`, never against a fixed number) and `track_id` (null when no tracker ran). `track_ids` lists the ids seen with a box.

Container tags are never read, so no location data reaches a sidecar. `uv run python tools/validate_sidecars.py RUN_DIR` checks every sidecar of a run against the schema plus the time and box relations a schema cannot state. Display-matrix flips: the upright frame the detector sees (and so every box) is checked against ffmpeg's own autorotate for all rotations and flips (`tests/test_t1a.py`, `tests/test_t5a.py`).

## Sound cues (T7)

`inframe cut VIDEO --sound snap --markers clap` reads the audio (`src/inframe/audio.py`, the onset method is spectral flux, peaks above a moving median + 4 MAD; numpy and scipy only, no model) and finds impacts: a board pop, a landing. Both flags are off by default, so a plain run is unchanged.

- `--sound snap`: each clip's start moves to 0.5 s before the earliest impact within 1.5 s of it, and its end to 0.5 s after the latest impact within 1.5 s of it. No edge moves more than 1 s, none crosses a neighbouring clip, none moves into a stretch where the target was seen (so a small `--pad` is never trimmed), and a start lands on the keyframe at or before the asked time when that is within the 1 s (a stream copy starts on a keyframe anyway, up to a GOP early; a pop is never cut off by the keyframe rule, because the keyframe is at or before the asked start). The old edges are kept in `clips[].snapped_from`.
- `--markers clap`: `clips[].markers` (kind, file time, strength) in segments.json, a `sound` object in the sidecar (schema 1.2, `docs/sidecar.schema.json`), `<marker>` elements in the FCPXML and OTIO markers in the OTIO-based edit lists.
- Confidence: with either flag, every clip gets `impacts` and `confidence` = peak score + 0.2 (capped at 1) when it holds at least one impact; `peak_score` is not changed.
- An impact needs a flux of 3 times its threshold. At 1.5 times a skateboard's rolling noise counts as impacts; at 3 times it does not. The value 3 is a judgement, not a measured optimum [unverified: no labelled pops].
- Slow motion: audio baked slow by a factor f makes impacts f times longer, so the search radius, lead and tail above are multiplied by f; the 1 s move cap and the 1 s minimum clip length stay absolute, so a misread f cannot move an edge more than 1 s. `--sound-speed auto` estimates f from how fast the strongest impacts rise (median 10 %-90 % rise time over 7 ms; below 3 counts as normal speed, above 8 is capped at 8). Soft-attack impacts at normal speed can still read as slow (rise time alone does not separate them) [unverified on real files]; the cap bounds the harm. That estimate is checked on synthetic clicks only (x4 gives 4, x8 gives 7, normal gives 1) [unverified on real slow-motion files]; `--sound-speed normal` or `--sound-speed 4` overrides it.
- No audio track: a warning in segments.json and on stderr, no error, exit 0.
- Not yet in the MCP `cut_video` tool.

## Highlight reel and edit lists

```
uv run inframe cut VIDEO.mov --reel --edit-list all --out OUT/detect     # with the cut
uv run inframe export OUT/detect --reel --edit-list fcpxml,edl [--out DIR]   # later, from a finished run's segments.json
```

- `--reel` joins the clips in time order into `<stem>_reel.<ext>` with no re-encode (ffmpeg concat, stream copy). Before the join each clip is copied (PyAV, packets untouched) without the pictures its edit list hides: the leading pictures of an open GOP (they need the previous GOP, so joined they would decode against the wrong frames) and the pictures decoded after the last picture inside the clip (a reference picture past the clip's end that is decoded earlier stays, so no B-frame of the clip loses its reference; the join then starts the next clip after it via a `duration` line in the concat list). The copy keeps the `hvc1` tag of the clips for HEVC (a bare PyAV template writes `hev1`, which QuickTime, Photos and FilmCraft on macOS refuse). For HEVC the first picture of each clip, a CRA, is rewritten as a BLA (one header byte per NAL unit), so the decoder restarts its picture count at the join. The reel is then checked against the original clips, not only the copies: it must carry the clips' codec tag and hold every picture each clip shows. It is checked from its packets: decode times increase in both streams, the first picture of each clip follows the last picture of the previous clip by at most 1.5 frames (no jump back, overlap or hole), and the audio starts within 21 ms of the picture at every join. If a join fails, the reel is built again with `-avoid_negative_ts make_zero` and checked again; a reel that still fails is kept and the run reports it (exit code 1). The result is in `segments.json` under `reel`.
- `--edit-list FORMATS` (comma separated, or `all`) writes edit lists of the cuts **on the original video**, frame-exact at the source rate (the clips themselves start at a keyframe): `fcpxml` (Final Cut Pro, FilmCraft, DaVinci Resolve), `fcp7` (Final Cut 7 XML, which Premiere imports), `kdenlive`, `edl` (CMX3600), `otio` (OpenTimelineIO JSON; Kdenlive 25.04 and later open it natively). In and out points are the clip start and end of `segments.json` (seconds from the container start) plus the container's start_time, rounded to whole frames. `edl` is written only at 60 fps or below and only at SMPTE rates (23.976, 24, 25, 29.97, 30, 50, 59.94, 60), `fcp7` only at those rates too, because the writers need a timecode; other sources get a warning and `skipped` in `segments.json` under `edit_lists`. Each file is read back with OpenTimelineIO and compared with `segments.json`: every cut must land within one frame. The FCPXML file is written by inframe (FCPXML 1.8, one asset, one event with one project) because the OTIO FCPXML adapter writes asset-clip and project elements where the format does not allow them; the OTIO reader is still used to read it back, except at fractional rates (29.97, 59.94), where that reader keeps only the whole part of the rate, so the times are read straight from the XML. The Kdenlive adapter is deprecated by its authors and fixes a 1920x1080 profile, which inframe replaces with the source's displayed size.
- Not verified: opening the FCPXML in FilmCraft and DaVinci Resolve, the FCP7 XML in Premiere, the Kdenlive file in Kdenlive. The checks above are the file-level ones.
- Names: `<stem>_reel.<ext>`, `<stem>.fcpxml`, `<stem>_fcp7.xml`, `<stem>.kdenlive`, `<stem>.edl`, `<stem>.otio` in the output folder. A later run in the same folder removes the ones it does not rewrite. `export` writes `export.json` next to its outputs.

## Pick videos from Photos (no Full Disk Access)

```
uv run inframe photos pick                                  # opens Apple's photo picker; pick videos, click Add; each is cut
uv run inframe photos pick -- --target photos:DIR --reel    # everything after a bare -- goes to `inframe cut`
uv run inframe photos pick --no-cut                         # only export the picked originals and print their paths as JSON
```

`photos pick` opens PHPicker, the picker Apple built for apps that must not see the whole library: videos only, several at once, preferred representation `current` (the file as stored, no transcode). macOS gives the helper only the items you pick, so **neither Full Disk Access nor library-wide Photos permission is needed**. The helper exports the originals into a temp folder, inframe runs the normal `cut` on each and then removes the folder (`--keep` or `--export-dir DIR` keeps them; `--no-cut` always keeps them). Clips and `segments.json` go to `./<video stem>_inframe/<mode>` in the folder you ran it from, or `--out` after the `--` (one subfolder per video when you pick several; two picks with the same file name get `_1`, `_2`). The cut options (numbers, `--edit-list`, `--target`) are checked before the picker opens, and the exported originals are removed on every way out, Ctrl-C included; a reused `--export-dir` has its numbered folders replaced. Close the picker window to cancel (exit 1, nothing cut); a helper or build failure exits 2. Equal to `cut` otherwise: the slow-motion `photos` block of `segments.json` is only written for `photos:<uuid>` refs, so a picked slow-motion file is cut at its own clock.

- **The helper** is `src/inframe/swift/photo_picker.swift` (about 120 lines, own code, only Apple system frameworks: AppKit, PhotosUI, UniformTypeIdentifiers). It is built on first use with `swiftc` (Xcode command line tools: `xcode-select --install`; no Xcode project) into `~/Library/Caches/inframe/bin/inframe-photo-picker-<hash of the source>`; editing the source rebuilds, `INFRAME_BIN_DIR` moves the cache. It prints `{"cancelled": ..., "files": [{"path", "name"}], "errors": [...]}` on stdout. No open-source command-line PHPicker helper with a permissive license exists (searched 2026-10-15: only iOS libraries, Flutter plugins and the batch exporter PhotosExporter), so this is a new file; no dependency is added.
- **Not verified:** that the picked file of a slow-motion video is the 120 or 240 fps original rather than Photos' 30 fps rendering, and iCloud-only items (the picker downloads them while exporting, which can take a while); both need a pick of a slow-motion original in a real library. [unverified]
- **Tests** run the Python side against a fake helper (`INFRAME_PICKER_HELPER` names an executable to run instead of the Swift build; it gets `--out DIR [--limit N]`) and compile the real helper once, checking `--version`. The picker window itself is never opened in tests.

## Save the exported clips and reel to Photos (add-only, no album)

```
uv run inframe export RUN --to-photos                  # the run's clip files go to the Photos library
uv run inframe export RUN --reel --to-photos           # the clips, then the reel just built
uv run inframe export RUN --reel --music auto --to-photos
```

`--to-photos` is also an argument of the MCP tool `export_reel` (`to_photos=true`), and the My Mac export dialog has **Save to folder** (the default) and **Save to Photos**; the browser engine keeps **Download** (a zip), because a web page cannot add to your library. The files are made as before, in the same folder, and are then added to the **Photos library** (no album). They stay in the folder.

- **iCloud.** Photos is not a local folder: with **iCloud Photos** on, every saved clip and reel is uploaded to Apple's servers, so the footage leaves this Mac. The export dialog says so next to the Save to Photos choice, and `inframe export --help` and the `export_reel` tool description say so as well. An MCP client that calls `export_reel(to_photos=true)` can do this without a click once the add-only permission has been given, so turn iCloud Photos off (or do not allow the permission) if the footage must stay here. [unverified: the upload itself, it was not tested]
- **Timeout or crash.** The helper prints one `{"row": ...}` line per file as soon as that file is in the library and the summary last. If it runs past 900 s (the permission dialog waits inside that time) or dies partway, the result is `interrupted`, not `failed`: it names the videos already added and says the others may or may not be in Photos, so check Photos before exporting again (a second save would duplicate them; Photos does not dedupe).
- **Reel-only.** With Clips unticked, only the reel goes to Photos; if the reel fails its check, nothing is saved (the fallback clips stay in the folder only).
- **Permission.** The helper asks macOS for `PHAccessLevel.addOnly`: it may put videos into the library and **cannot read the library**. No Full Disk Access, no library-wide permission. The first save shows macOS's own dialog; it names the app that runs inframe (Terminal, your editor), because macOS attributes the request to the program that started the helper. Allowing it later: System Settings > Privacy & Security > Photos, then pick the add-only choice for that app.
- **When permission is denied** (or the Mac restricts Photos) nothing is saved and every surface says so in one sentence that names the setting: `inframe export` exits 1 and prints it to stderr; `export_reel` returns `photos.status = "denied"` with the same `message`, which is also added to `warnings` (the reel itself is kept); the export dialog shows it as an alert under the list of written files, and the export.json of the run holds the `photos` block. A save that worked for some files only is `partial`: the names saved and the names that failed (with the system's reason) are listed. The export itself never fails because of Photos.
- **What is saved.** Clip files that were cut (not the sidecars, CSV or edit lists) and the reel when it passed its check. Each is one `PHAssetCreationRequest` with the file added as a video resource (`shouldMoveFile = false`, so a copy goes in); one failing file does not stop the others.
- **The helper** is `src/inframe/swift/photo_save.swift` (about 100 lines, own code, only the Photos system framework) with `photo_save_Info.plist` linked into the binary (`-Xlinker -sectcreate __TEXT __info_plist`): macOS refuses to show the Photos dialog for a program that has no `NSPhotoLibraryAddUsageDescription`. It is built on first use with `swiftc` into `~/Library/Caches/inframe/bin/inframe-photo-save-<hash of source and plist>` (`INFRAME_BIN_DIR` moves the cache) and prints one `{"row": {"path", "saved", "error"}}` line per finished file, then `{"authorization", "status": "saved"|"partial"|"denied"|"failed", "files": [{"path", "saved", "error"}], "message"}`; exit 0 when something was saved, 3 when denied, 1 otherwise. `photo_save.py` is `src/inframe/photosave.py`. No dependency is added.

## Videos from the Photos library

`photos list` and `cut photos:<uuid>` read the library with osxphotos and **need Full Disk Access** (kept for others; without it use `photos pick` above).

```
uv sync --extra photos                       # osxphotos 0.77.2 (MIT), macOS only; the dev group has it too
uv run inframe photos list --since 2026-10-01 --slomo     # uuid, date, slomo, path of the original (or MISSING)
uv run inframe photos list --json
uv run inframe cut photos:<uuid>             # cuts the original in place; output in ./<uuid>_inframe/detect
```

Only five fields are read: `uuid`, `date`, `slow_mo`, `ismissing` and `path`. No location, people, albums, keywords or file names are read, printed or written. The original is cut where it lies; clips and `segments.json` go to `./<uuid>_inframe/<mode>` (or `--out`), never into the library. `--library <path>` picks a library other than the one Photos opened last.

- **Full Disk Access.** macOS blocks the library until the app that runs inframe (Terminal, an editor) has it. Without it `inframe photos list` and `inframe cut photos:...` exit 2 with the steps (System Settings > Privacy & Security > Full Disk Access, then reopen the app). Only the person at the Mac can grant it.
- **iCloud-only originals.** If `ismissing` is true the cut stops with the way to download the original in Photos (File > Download Original); the list shows the video as `MISSING (iCloud only)`.
- **Slow motion.** A slow-motion original is a 120 or 240 fps file that Photos plays at 30 fps. inframe cuts it at its own (real-time) clock, so `clips`, `presence_intervals` and the clip names stay in source seconds. `segments.json` gets a `photos` block (`uuid`, `date`, `slow_mo`, `time_map`) and, in every clip, `playback_start`/`playback_end` (source seconds times the factor). The factor is one constant, capture fps over 30 (240 fps gives 8, 120 gives 4): the ramp inside Photos' slow-motion edit cannot be read from the file. Retiming the clips themselves is `--slowmo`, below.
- **Same tries as the 30 fps export.** `uv run python tools/check_tries.py <original segments.json> <export segments.json>` checks that the original gives the same number of tries in the same order as the export of that session, with the original's times mapped through the factor. A boundary may differ by 0.3 x (1 + factor) playback seconds: 0.3 s on the export's own timeline plus the 0.3 s of real time of the regression contract, stretched by the factor. It prints PASS or FAIL and exits 1 on FAIL.
- **Real-library check (pending).** `uv run inframe photos list --slomo` in a Terminal with Full Disk Access, then `uv run inframe cut photos:<uuid of a slow-motion session>` and the same session's 30 fps export cut as a file, then `uv run python tools/check_tries.py <original>/segments.json <export>/segments.json`.
- **Tests** fake osxphotos' `PhotosDB.photos()`; set `INFRAME_OSXPHOTOS_TEST_LIB` to an osxphotos test library (osxphotos' own `tests/Test-*.photoslibrary`, MIT) to also run the one test that opens a real library file. Neither touches your Photos library.

## Slow-motion playback (`--slowmo`, T3c)

```bash
uv run inframe cut original.MOV --slowmo auto            # 240 fps file -> x8, 120 fps -> x4, a 30 fps file is left alone
uv run inframe cut original.MOV --slowmo 4 --slowmo-audio # a fixed factor; keep the audio, stretched
```

A 120 or 240 fps original, cut as it is, plays at its own (real-time) speed. `--slowmo auto|4|8|off` (any factor above 1 works; default `off`) makes each clip play slowly instead: it lasts `factor` times longer and its frame rate drops to 1/factor (240 fps at x8 is 30 fps, at x4 60 fps). `auto` is the capture rate over 30 fps, one constant factor for the whole clip, because the speed ramp inside a Photos slow-motion edit cannot be read from the file; a file under 100 fps (ordinary 30 or 60 fps video) is not retimed, and the factor is capped at 100 and the run says so. `inframe cut photos:<uuid> --slowmo auto` leaves a video that Photos does not mark as slow motion alone.

- **The picture is never re-encoded.** After the usual two stream-copy passes, a third pass multiplies the video timestamps by the factor with ffmpeg's `setts` bitstream filter. The scaling is anchored at the first picture, so it stays where the align pass put it. The picture packets are byte-identical to the unretimed cut (checked by md5 of the copied packets); rotation, the `hvc1` tag and HDR flags are kept.
- **Audio** is dropped by default (a slowed track of the original would not match). `--slowmo-audio` keeps it, stretched with `atempo` at the same pitch and re-encoded to AAC 128k: the only re-encode, and only of audio. It starts half an AAC frame late so the first audio packet sits 10.7 ms from the first picture (the AAC encoder's priming would otherwise put it 21.3 ms away, over the 21 ms limit). `--slowmo-audio` without `--slowmo` is refused (exit 2).
- **`segments.json`** gets a top-level `slowmo` block (`requested`, `factor`, `capture_fps`, `audio`: `dropped`, `atempo` or `none`, `rule`) and in each clip a `slowmo` block with the clip-time to source-time map: `clip_s = (source_s - source_t0) * factor`, so `source_s = source_t0 + clip_s / factor`, with `source_t0` the clip's `expected_copy_start`, and `clip_start_s` 0. It also records what ffprobe measured on the finished clip: `duration_s`, `fps`, `has_audio` and `av_offset_ms` (first audio packet minus first picture; a run warns when it is beyond 21 ms). `start`, `end` and `presence_intervals` stay in source seconds, and so does the sidecar's `clip_time`; the sidecar (schema 1.2) gets an optional `slowmo` block with the factor and the played duration.
- **Reel, edit lists:** the reel joins the retimed clips like any others. With `--music --beat-sync` a clip's trimmable tail is counted in played seconds. Edit lists describe the original video's cuts at source speed.
- **MCP:** `cut_video(..., slowmo="auto", slowmo_audio=False)`; each clip in the result carries its `slowmo` block.
- No new dependency: ffmpeg only. Tests: `tests/test_t3c.py` (synthetic 240 fps HEVC with audio, generated by ffmpeg).

## Music for the reel (T4b)

```
uv sync --extra music                                       # librosa, only needed for --beat-sync
uv run inframe music list                                   # the songs that come with inframe (offline, no request)
uv run inframe music search --mood upbeat --min-seconds 90  # more songs, online: CC0 and CC BY tracks (add --cc0-only for CC0 alone), with their license
uv run inframe music get TRACK_ID [--cc0-only]                 # -> ~/Library/Caches/inframe/music/TRACK_ID.mp3 + TRACK_ID.json
uv run inframe export OUT/detect --reel --music TRACK_ID_OR_FILE [--cc0-only] [--beat-sync] [--out DIR]
uv run inframe export OUT/detect --reel --music auto[:MOOD] [--music-rank N] [--cc0-only] [--no-beat-sync] [--out DIR]   # inframe picks the song
uv run inframe cut VIDEO ... --music auto[:MOOD]|FILE|ID [--music-rank N]               # cut and build the reel with music in one go
uv run inframe music auto OUT/detect [--mood M] [--rank N] [--json]                      # the ranked songs, without building a reel
```

- **Songs that come with inframe (`src/inframe/music_library/`, `musiclib.py`):** eight songs (all CC BY 3.0, 24.96 MB in total, seven of them converted to AAC 160 kbit/s to fit 25 MB) ship inside the package, so auto music, `music list` and the music dialog of `inframe serve` work offline and download nothing. `library.json` has each song's title, artist, license, license URL, source URL, length, BPM, loudness, mood tags, size and SHA-256; `CREDITS.md` has one title-author-source-license line per CC BY song. `tools/build_music_library.py` made the library: it searches Openverse (Jamendo) for CC0 and CC BY 3.0 or 4.0 only (never BY-SA, BY-ND or NC), 60 to 240 s long, measures length (ffprobe), tempo (librosa, through `inframe.beats`) and loudness (ffmpeg `ebur128`) by code, picks songs that differ in tempo and mood within 25 MB in total, keeps the original file when the budget allows and otherwise converts it to AAC 160 kbit/s (the credits say which). The BPM in `library.json` is librosa's strongest periodicity (flat prior, folded into 70 to 180), so a song can be listed at half or double its felt tempo [unverified: not compared with a human count]. That number is the song's one BPM everywhere (the dialog, `music list`, the reel's record and the tempo term of the auto music score, with or without the `music` extra); auto music still analyses the audio with `inframe.beats` for the beats it cuts on and for the other score terms, but its own tempo estimate is not used for a bundled song (it disagreed with the library's by up to 40%, not by an octave). The build skips the ids in `EXCLUDED` ("Jingle bell rock", id 22a0cd91, was replaced on 2026-10-17: its title is that of a 1957 song in copyright, and if it was a cover a CC BY label cannot license the composition; whether it was one is [unverified]), and it strips an embedded album cover from an original file (a separate work with no license on record; the audio is copied bit for bit and CREDITS.md says so). The replacement, "Higher - Funk version" by zero-project, passed the same automatic checks and has not been listened to or compared with known works [unverified]. `tools/build_music_library.py --verify` re-checks the committed files offline. A bundled song's id is its Openverse id, so `--music ID`, `music get` and the serve routes find it without a request. **Auto music uses them first:** ranks 0 to 7 are the bundled songs (best fit first, scored like any other song), and only "another song" past the last one ("more songs" in the dialog) searches Openverse. With `INFRAME_MUSIC_OFFLINE=1` or no network, the bundled songs still play and the list ends on the built-in beat. `--cc0-only` leaves only the CC0 bundled songs (`INFRAME_MUSIC_LIBRARY=off` turns the bundled songs off, `INFRAME_MUSIC_LIBRARY=/folder` reads another library; the tests use `off`).
- **Source (more songs, online):** the Openverse audio API (api.openverse.org, no key), `source=jamendo` for full songs. **CC0 and CC BY by default (decided 2026-10-16; CC0 alone found nothing):** Openverse has no CC0 tracks in its music category, so CC0 alone found nothing. `music search`, `music get` and `export --music TRACK_ID` ask for and accept CC0 and CC BY tracks; a CC BY track's credit is written automatically (below), with no flag. `--cc0-only` restores the old rule (the web export dialog has a "CC0 only" box, off by default): `music get` and `export --music` then refuse a CC BY id, also when it is already in the music cache, with a message that names the flag. `--allow-by` is still accepted and does nothing, so old commands keep working. A track file you pass yourself with its `.json` is not checked, except that `--cc0-only` refuses one whose `.json` says CC BY. Each query asks for one license (`cc0`, then `by` unless `--cc0-only`; a comma list returns nothing) and the result is filtered again in code: only `cc0` and `by` stay, so `by-sa`, `by-nd` and `by-nc*` are always dropped. The license is read from the Openverse record of the track when it is downloaded (never from a search row), and a cached record that names any other license is refused. `music get` stores the file with a JSON of the license, the license URL, the creator and the ready-made attribution line. Openverse indexes metadata and does not check licenses, and Jamendo tracks may be claimed by Content ID systems [unverified]. **Openverse notice (its terms of service):** inframe uses the Openverse API and is not endorsed by Openverse; CC works must be credited (below); no scraping of the catalogue and no spreading requests over several machines to dodge rate limits; Openverse may charge for heavy or commercial use. Anonymous use is rate-limited (HTTP 429 gives a one-line message); the limit is not documented [unverified]. Checked live on 2026-10-15: the search call (`inframe music search`) and the detail record of one track (fields, license, attribution). **Not checked live:** the mp3 download itself (`music get`), which is tested against a stub. A local file works too: `--music song.mp3` uses `song.json` beside it as its license record when that exists.
- **`--music`:** the reel's only sound is the music; the clips' own audio is dropped. It is cut to the reel's length (or looped when shorter), faded in (0.5 s) and out (2 s), and set to -14 LUFS: a gain computed from the measured integrated loudness (ffmpeg `ebur128`) followed by a limiter at -1 dBFS, measured again until it is within 0.3 LU, then AAC 256k, 48 kHz. The report's `lufs` is measured on the finished reel. Very peaky music cannot reach -14 LUFS under that peak limit (a bare click track stays about 5 LU too quiet); the reel is then reported as FAILED with the number, not silently quiet.
- **Plain reel with music:** the lossless reel of `--reel` (stream copy), with its sound replaced.
- **`--beat-sync`:** beat times come from librosa (`onset_strength` with a 512-sample window at a hop of 64, then `beat_track`; on synthetic click tracks at 100-128 BPM the beats are within 6 ms of the clicks). The reel starts on the music's first beat; each clip change lands on the latest beat that keeps the clip between its full length and its length minus its tail padding (`end` minus the last presence interval, normally `--pad`), so only padding is trimmed. The beat is rounded to the nearest picture, so a join is at most half a picture from it. A track shorter than the reel loops between its first and last beat, so the seam is on the grid. If no beat falls inside a clip's padding the clip is cut at the latest beat before its end and a warning says how far into its content; a clip shorter than the gap between beats is joined off the beat and reported as a problem. Downbeats are not detected: a join lands on any beat, not on a bar line. Landing exactly on a beat needs whole-picture cuts, so the clips are decoded, trimmed (`trim=end_frame`), joined (`concat` filter) and encoded once with `hevc_videotoolbox` at `-q:v 85` (libx265 at CRF 14 where that encoder does not exist). On a 17 s phone clip (8.2 Mb/s source) q 75 gave 1.7 Mb/s at 46.4 dB PSNR, q 85 gave 4.5 Mb/s at 49.7 dB and q 92 gave 13.1 Mb/s at 54.5 dB. The picture keeps `hvc1`, the pixel format (yuvj420p), the colour range, space, transfer and primaries, and the display rotation (set again with `-display_rotation` at the final copy, because the encoder does not carry it).
- **Checks, run on every reel and written to `export.json` (`reel.check`):** one video and one AAC stream; loudness within -14 +-1 LUFS; rotation and colour tags equal to the clips'; video and audio the same length; with beat sync, the reel has the planned number of pictures and each join (the packet time of the first picture of the next clip, from ffprobe) is within 1 picture of its beat (`max_join_err_frames`). Informational: `audio_beats` finds the beats in the reel's own sound and gives the median distance of the joins to the nearest one; its maximum is large because the last join sits in the fade-out.
- **`<video>_credits.txt`** is written next to the reel whenever the music is CC BY (every export path: CLI, the web UI), with no flag: title, creator, the attribution line, license and its URL, the creator and source pages, and the Openverse notice. CC0 needs none. The same text is in `export.json` (`reel.music.credit_text`, with the file name in `reel.music.credits`), in the reel file's comment tag, and the web export dialog shows it with the file name after the export. A music file without a license record gets a warning and no credits file. It is removed by the next `cut` into the same folder, and by any later `export --reel` of the same video (a reel with CC0 music or none keeps no credit of an earlier reel's song), like the other exports.
- **Auto music (`--music auto[:MOOD]`; MCP `export_reel(run, music="auto")`; design in `docs/AUTO_MUSIC.md`):** inframe picks a free song that suits the reel and fits it (trim or loop, fades, -14 LUFS, cuts on the beat; beat sync is on by default when librosa is installed, `--no-beat-sync` turns it off). No LLM and no new dependency. **Only the mood word (the Openverse search text; default `calm`, `upbeat` or `energetic` from how many clips a minute the reel has: under 4, 4 to 10, 10 or more) and the track downloads leave the machine**; the reel's shape never does. **Scoring:** candidates are the Jamendo rows of the search that are CC0 or CC BY (CC0 only with `--cc0-only`), 30 to 600 s long and not marked mature. They are ordered by a metadata score `0.45 L + 0.30 S + 0.15 M + 0.10 I` (length against the reel, Jamendo speed tag against the wanted speed, mood word in the tags or genres, instrumental 1.0, no tag 0.8, vocal 0.6; ties go to CC0, then the id). With librosa the first 4, then 2, then 2 of them are downloaded in fixed batches and scored `0.35 J + 0.20 Lp + 0.15 Tb + 0.15 P + 0.10 Q + 0.05 meta`: J is the share of clips whose end can land on a beat inside its padding (the beat-sync plan itself), Lp the length term with the real length, Tb the tempo against the speed's band (folded BPM), P the beat strength, Q the loudness of the 10 s after the first beat against the song. Each batch is sorted by that score, so a rank never moves once given; **the built-in beat (CC0, rendered by `synthbeat.py`, 120 s, BPM chosen from the speed's choices by J) is always the last entry**, so there is always a song, also when Openverse cannot be reached or no free song is found. Without librosa the metadata order is used, only the chosen song is downloaded and beat sync stays off (a warning says so). **"Another song"** is `--music-rank N+1` (CLI), `music_rank` (MCP; the result's `another_song` is the call), and past the end of the list it wraps. `reel.music.auto` in `export.json` has `{rank, n, mood, speed, score, bpm, builtin, wrapped}`, and `reel.music.title` and `creator` name the song; a CC BY pick gets its credits file as always. **Caps and request budget (anonymous Openverse: 20 a minute, 200 a day):** at most 8 downloads per (reel shape, mood, `--cc0-only`); at most 4 search requests per query (2 pages for each license) and one more query (`instrumental`) when fewer than 5 rows pass; the kept rows are cached 7 days, so the same mood costs no search request; analyses are cached; the songs auto music downloaded are kept to 500 MB or 60 tracks (least recently used go first, a `music get` download never does). A new mood costs about 3 search and 4 detail requests. A rate-limit answer falls back to an older search cache, then to the built-in beat. `INFRAME_MUSIC_OFFLINE=1` sends no request at all (caches and the built-in beat only). `--cc0-only`: Openverse has no CC0 music, so the choice then normally ends on the built-in beat. [unverified] A real song with this scoring has not been run through the beat tracker: the ranking was checked on synthetic songs only, and no real track was downloaded.
- **Measured** on test clips (synthetic 124 and 128 BPM tracks from `tools/synth_music.py`; no real recording was used): every join of the beat-synced reel within 0.5 picture (16.6 ms) of a beat, -14.1 LUFS, one hevc and one AAC stream, `hvc1`, yuvj420p/pc/bt709. Export time depends on the video and the machine; measure it on your own clips.
- Real music was not run through the beat tracker in this part [unverified]: a real song can make `beat_track` lock to half or double time, which moves joins to every second or every other beat but keeps them on a beat. If the beats sound off, the runner-up is `beat_this` (MIT code, needs PyTorch, checkpoint license not read).

## MCP server

`inframe-mcp` is a stdio MCP server (official Python SDK, `mcp`, MIT) so Claude Code can call inframe. Inputs and outputs are absolute local paths and numbers, never video bytes. Add it to Claude Code yourself:

```
claude mcp add inframe -- uv --directory /path/to/inframe run inframe-mcp
```

Tools:

- `probe_video(path)`: codec, stored and displayed size, rotation, fps, duration, audio, keyframe spacing. Stream facts only; container tags (location) are never read or returned.
- `list_people(path, out=None, min_seen=1.0, max_people=20)`: one detect + track pass (balanced preset, needs `uv sync --extra tracking`) that lists the people the tracker followed, longest in frame first. Per person: `person`, `track_id` (only meaningful inside this scan), `first_s`, `last_s`, `seen_s`, `stretches`, `thumbnail` (absolute path of a JPEG crop of the person's best sample) and `target`, a string for `cut_video`. Writes `people.json`, `person_NNN.jpg` and `person_NNN.json` (a target.json: time, box, track id) into `out` (default `<stem>_inframe/people`). A person the tracker loses and finds again may be listed twice; pass both targets to `cut_video`. Shares the one-job-at-a-time lock with `cut_video`, and reports progress.
- `cut_video(path, mode="detect", preset="balanced", pad=1.0, min_len=1.0, merge_gap=1.5, reel=False, edit_lists=None, out=None, target=None)`: the same cut as `inframe cut` (`target` as `--target`: a person's `target` string from `list_people`, `tap:T,x,y`, or `photos:<abs folder>`, or a list of them; detect mode only; paths must be absolute; `reel` and `edit_lists` as `--reel` and `--edit-list`; their results come back under `reel` and `edit_lists` with absolute paths). Returns `clips` (absolute file path, start, end, duration, peak score), `presence_intervals`, `segments_json`, `out_dir`, `kept_s`, `warnings`, `timing_s`. A 20 minute video takes about 2 minutes, and the tool sends MCP progress notifications (0-100) while it runs. One cut runs at a time; a second call gets a "run in progress" error.
- `list_targets()`: the saved targets (see Saved targets): name, number of crops, dates, sources, stored embedder versions. `cut_video(target="saved:NAME")` keeps that person with no tap; when the run found them the result has `saved_target` and `add_crops`.
- `add_target_crops(name, run, embedder="dinov2")`: adds crops of the person a finished run found (`run` = its segments.json or folder) to the saved target `name`, deduplicated and capped.
- `export_reel(run, music=None, music_rank=0, beat_sync=None, cc0_only=False, edit_lists=None, out=None)`: builds the reel of a finished run (`run` = its segments.json or folder), with `music` = `"auto"`, `"auto:MOOD"`, a track id or an absolute audio file (see Music for the reel). `beat_sync=None` is on for auto music when librosa is installed. Returns `reel` (with `reel.music.auto`), `edit_lists`, `warnings`, `export_json`, and for auto music `another_song`. Only the mood word leaves the machine. Shares the one-job-at-a-time lock.
- `compare_runs(a, b, min_len=1.0, out=None)`: `a` and `b` are segments.json files or their run folders. Returns the comparison and the paths of `compare.json` and `compare.md`; refuses runs of different videos.

Round trip on a composite (T1d, `tests/test_t1d.py`, two_side from `tools/splice.py`, 38 s, 190 samples): `list_people` then `cut_video(target=[the listed people standing in the target's tiles])` over stdio gave time-weighted precision 1.0 and recall 0.966 against the composition truth (people chosen by the truth's tile roles, not by looking at thumbnails). The test skips when the composite, the models or the tracking extra are missing.

Bad paths (not absolute, missing, a folder, not a video), a bad `mode` or `preset`, a bad `target`, and negative or non-finite numbers come back as tool errors with a one-line message, before anything is written.

## Zone and activity (T6)

```
inframe cut VIDEO --zone 0.2,0.3,0.5,0.6                 # only people whose box centre is in this rectangle count
inframe cut VIDEO --zone 0.2,0.3,0.5,0.6 --zone-overlap 0.3   # ... or at least 30 % of the box
inframe cut VIDEO --activity riding                      # a person counts only while their box moves fast enough
inframe cut VIDEO --activity riding --slowmo-factor 8    # a baked 8x slow-motion file: speeds are per REAL second
```

- **Zone** (`x,y,w,h`, each a fraction 0..1 of the *upright* frame, 0,0 = top left, the picture as a player shows it). Frames, boxes and the motion mask are upright after the display matrix (rotation and flip) is applied, so a zone is simply a rectangle of what you see, for rotation 0, 90, -90 and 180 alike (tests/test_t6.py draws a box at a known stored position in each and checks the zone). It can also be drawn on the `inframe pick` page (**Draw zone**, drag a rectangle; it is written into `target.json` and `cut --target tap:target.json` uses it unless `--zone` is given). Detect mode: a person counts when the box centre is inside (or `--zone-overlap F`: at least F of the box area). An "any person" target filters the candidates first, so a bystander outside the zone cannot hide the person inside; a tap or photo target is decided on all the people, and its answer is dropped when its box is outside. Motion mode: the score is the fraction of the zone's pixels that changed.
- **Static camera only.** Before the run, `camera.py` compares the video's keyframes with their per-pixel median (phase correlation, the estimate motion mode uses). If the p95 shift is over 1.5 px at 320 px wide, the run warns (in `segments.json` `warnings` and on stderr) and ignores the zone. `segments.json` `settings.camera_check` holds the numbers and `settings.zone_applied` the zone that was used (null when ignored).
- **Activity.** `--activity riding` keeps a person only while their speed is at least `--activity-threshold` (default 1.65) box heights per real second: the distance the box centre moves between two samples, in box heights, per second, multiplied by `--slowmo-factor` (a file that plays F times slower than real time), then the median of the steps within +-0.5 s (1 s). A person with fewer than two steps has no speed yet and is kept. The people are followed by the module's own centre-distance matching, not by the tracker, because an IoU tracker at 5 samples/s loses a rider; so it needs no tracking extra, but it needs 2+ samples per second (the fast preset's keyframes are too sparse: a warning, and nobody is dropped). Detect mode only. The speed is measured in the picture, so it assumes a static camera too (a following or shaking camera gets a warning). The threshold came from `tools/activity.py` (synthetic boxes and sliding person clips, never the regression video). `--slowmo-factor` is a plain number for now; T3's `--slowmo` will fill it in.
- MCP `cut_video` takes `zone`, `zone_overlap` and `activity`.

## Any object: `--target class:NAME` (T8a)

`inframe cut VIDEO --target class:dog` keeps every stretch with a dog in frame; `--target class:dog --target tap:T,x,y` (or `inframe pick VIDEO --class dog`, whose target.json records the class) follows the one dog you tapped, with the same tap machinery as for people (tracker, bridge, appearance match). Any of the 80 COCO classes works (`src/inframe/classes.py` has the id table: the RF-DETR COCO checkpoints use ids 1-90 with gaps; case, `_` and `-` do not matter, and a few aliases such as `bike`, `phone`, `sofa` are accepted). `class:` also works as an MCP `cut_video` target. A class other than person never runs on nano (`--preset fast` gets small); a tap on a box under 80 px high in the model's input moves to base when its CoreML package exists (`base_coreml_b1`, exported by bench/detect). `segments.json` settings record `class`, `class_id` and `model_note`. Measured on two dog composites: precision 0.960, recall 0.956 for one dog among other dogs; dog against dog inside one clip is unmeasured. No new dependency, so nothing new in the license list.

## Tap mode: follow one person

```
inframe pick VIDEO                      # opens http://127.0.0.1:PORT/ in your browser (--no-open: only prints it); click the person in a numbered box; Done writes <video>_inframe/target.json
inframe cut VIDEO --target tap:VIDEO_inframe/target.json
inframe cut VIDEO --target tap:12.4,0.52,0.60      # or a tap by hand: seconds, then x and y as fractions (0..1) of the upright frame
```

`pick` is a stdlib `http.server` page on 127.0.0.1 (plain HTML/JS, no extra dependency): a slider over the video, the detector's boxes numbered on the frame, and a click on a box saves it as `target.json` (`time`, `box`, `track_id`, and a `taps` list; click in several frames for several appearances, Undo removes the last one). `model` and `preset` record the detector the box was found with: `cut --target tap:target.json` defaults to that preset and refuses another detector (`--preset balanced` after `pick --preset accurate` exits 2), because the other model may not find the tapped person again. `track_id` is the id a short tracker window before the tap gave the box (null without the tracking extra); `cut` finds the person again from the box, because ids differ between runs. `--target` can be repeated, one tap per appearance of the same person. It needs `--mode detect`.

How `pick` stays fast and quiet (pick-ux): the slider waits about 300 ms after you stop moving before it asks for a frame and shows "loading" meanwhile; the page cancels the request it no longer needs; the server decodes and detects on one worker thread and serves only the newest request (a request that a newer one replaced before the worker started it is dropped with HTTP 409 and never decodes or detects); frames and boxes are cached per time (48 frames, least recently used out); the detector is loaded when the page opens. `pick` and the pipeline runs use the same `CPU_AND_GPU` default; set `INFRAME_DETECT_UNITS` (`CPU_ONLY`, `CPU_AND_NE`, `CPU_AND_GPU`) to override it. A browser that cancels a request or closes the tab is a normal event and prints nothing; the coremltools, scikit-learn and torch version notes are kept off the terminal. The terminal says `waiting for your tap...` and how to stop (Done on the page, or Ctrl-C). The first request of a run is the model load (21-80 s on a busy Mac, the same before and after); the page now starts it when it opens. No new dependency (stdlib `webbrowser`, `collections`, `logging`).

Exit 2 with a message when no person was detected within 1 s of a tap, or the spec is not a target.json or `T,x,y` (exit code 2 is also the usage error of the other commands).

What the run does with a tap (src/inframe/tap.py): the tapped detection's track is followed backwards and forwards (the tracker restarts at every hard cut, `tracks.frame_distance` above 0.3, and nothing carries over a cut), holes in the target's presence are bridged from the last box that was chosen: for up to 2 s (10 samples) in the same shot, a detection with no track, or on a track too short to have been judged by its look (under 3 samples), that overlaps that box (IoU 0.1) or lies 80 % inside it (a person leaving at the frame edge) is taken, and the chain follows that person; a short track that starts within 2 s of an accepted one ending (or ends within 2 s of one starting), where it ended, is stitched on whatever its clothes look like, and any other track in the run whose clothes match the tapped one (a colour histogram of the upper and lower body, similarity 0.70 or more (0.65 for a track of 3 s or more), never together with an accepted track in the same frame) is taken as the same person. Without a tracker (fast preset, under 5 samples per second) the match is per sample by position and clothes. `segments.json` records `target_info`: taps, tracks accepted, and the tracks that nearly were. Measured on the spliced composites: precision 1.000 and recall 0.830 in the shots that got a tap; recall is capped by the detector in small tiles and does not reach 0.95 everywhere. It finds the person again after a gap, not after a change of clothes (T1c).

## Targets, tracking and models

A target is stateful: `evaluate(t, frame, candidates) -> Hit(score, box, track_id)` is called once per sample, in time order. `AnyPerson` is the only target so far and needs no identity. A target that sets `wants_tracks = True` gets a `track_id` on every candidate (`Detection.track_id`) from roboflow/trackers: OC-SORT by default, `--tracker botsort` when the camera pans. The tracker runs only at 5 or more samples per second (`tracks.MIN_TRACK_FPS`); the fast preset (keyframes only) matches the gallery per keyframe and has no tracker, and says so in `warnings`. When a tracker ran, `samples.csv` gets a `track` column. `uv sync --extra tracking` installs it; it is not in the default install or the dev group (see Licenses), so the tracker tests skip unless it is installed (`uv run --extra tracking pytest`).

`trackers` pulls in OpenCV, whose bundled FFmpeg clashes with PyAV's when both load in one process (macOS: "Class AVFFrameReceiver is implemented in both"). So the tracker runs in a child process (`inframe.track_worker`) and the main process never imports `cv2`.

Models: the detector looks in `$INFRAME_MODELS`, `./models`, the cache (`~/Library/Caches/inframe/models`, or `$INFRAME_CACHE/models`), then `bench/detect/out/models`; the first folder that holds the CoreML package wins, so a cache folder that only has the checkpoints is skipped. `inframe fetch-models` downloads the RF-DETR checkpoints into the cache with a progress bar and an md5 check, and keeps nothing that fails the check. The CoreML packages the detector runs are exported from those checkpoints by `bench/detect/setup.sh`; they are not published anywhere, so a missing package gets a message that says where to put it. `inframe cut --offline` never downloads: a missing model is a one-line error (exit code 2). The torch fallback loads its checkpoint from that same cache by explicit path (downloaded there with the md5 check when online), so `fetch-models` is enough for it and it does not depend on the current directory.

Developer tools (they need a reference clip of your own, set per machine with `INFRAME_REGRESS_VIDEO` and `INFRAME_REGRESS_BASELINE`, see `inframe.localcfg`; without it they print SKIP):
- `uv run python tools/regress.py` runs detect on the configured regression video and compares the presence intervals with the recorded baseline intervals (each boundary within 0.3 s). It prints one PASS/FAIL line and takes a lock (`~/.cache/inframe/regress.lock`) so two runs queue.
- `uv run python tools/splice.py build|score|ids|tap` builds the spliced composites and their truth, scores a run (time-weighted precision and recall), and measures ID switches (docs/TESTDATA.md).

- `uv run python tools/activity.py synthetic|slide build|slide score|real` calibrates and measures `--activity riding`.

## Review UI: `inframe serve` (T9a)

```
uv run inframe serve [VIDEO] [--port N] [--no-open] [--offline] [--keep-picked]
```

Starts a web server on `127.0.0.1` only (a free port unless `--port` is given) and opens the editor in your browser through a one-use link (the address holds a nonce in the `#` fragment; the page trades it for a session token, so no token sits in a URL, the history or `ps`). Nothing leaves the Mac: the page can only talk to this server, and the video is read in place (no upload, no copy). Press Enter in the terminal for a new link; a new tab needs a new link. Design, API and security rules: `docs/T9A_DESIGN.md`.

What the web shell does so far (part C1 of the build): open a video (native dialog on macOS, the built-in file browser, a pasted path, a dropped file looked up by name and size, a recent list), play it from the original with a measured file-time clock (a preview copy is made when the browser cannot play it), show the newest run of that video and its clips, and edit the clips with the keys (split, merge, delete, add, trim to the playhead, undo and redo, autosave to `edits.json` next to the run). Press `?` for the shortcut sheet. The timeline, the clip strip and the target, run and export panels come with the next build parts. The engine behind the page is an interface (`web/src/engine/types.ts`): `local.ts` talks to `inframe serve`, `mock.ts` is an in-memory engine for tests (`npm --prefix web run dev -- --mode mock`), `browser.ts` is the stub for the in-browser engine (T9b).

The built UI is committed in `src/inframe/web/dist/` so `uv sync` and `uv tool install` need no Node. To change it you need the Node version in `web/.nvmrc`:


## Browser mode

`inframe serve` has two engines, switched with the "My Mac" and "This browser" buttons (the choice is kept in the browser's localStorage `inframe.engine`). "This browser" runs the whole pipeline in the page: WebCodecs decodes the video, mp4box.js reads the MP4 or MOV in 8 MB slices, onnxruntime-web runs the models on WebGPU in a Worker, and the clips are cut by our own MP4 muxer and written as a zip. The video never leaves the browser: it is read in place from the file you chose, nothing is uploaded, and every request the page makes is a GET to the page's own origin (the tests check this). Only the model files come from the server, once. The editor, the cut list and the export are the same as with My Mac. Browser tap matching is simpler than My Mac's (no tracker; a look gallery), and how well it follows a real person is [unverified]. Design: `docs/T9B_DESIGN.md`.

**Models.** The first run downloads three files and keeps them in Cache Storage (Remove deletes them): `rfdetr_small_v1.onnx` (123.5 MB, RF-DETR small, Apache-2.0), `dinov2_s_v1.onnx` (88.4 MB, DINOv2-S, only for tap runs, Apache-2.0) and the onnxruntime-web runtime `ort-wasm-simd-threaded.asyncify.wasm` (26.8 MB, MIT). They are made by `tools/export_onnx.py` and served read-only by `inframe serve` under `/models/`. Licenses are under Licenses below.

**Browsers.** Google Chrome with WebGPU is the tested one. Safari (26.5 in the spike) runs both models on WebGPU but a whole run in Safari was not measured [unverified]; it builds the zip in memory, so an export above 2 GB says "use My Mac". Firefox has no HEVC decoding in WebCodecs, and the page says so. Without WebGPU the models fall back to the CPU, about 19 times slower, with a warning. Only H.264 and HEVC files can be cut.

**Measured limits** (Chrome, synthetic 1080p30 HEVC at 8 Mbit/s, balanced preset, any person):

| video | wall time | peak memory (whole browser) |
|---|---|---|
| 5 min | 95.6 s | 2225 MB |
| 20 min | 545.6 s | 2183 MB |
| 60 min | 1830.4 s | 2258 MB |

Memory stays near 2.2 GB from 5 to 60 minutes; time per video minute grows (19.1 s, 27.3 s, 30.5 s) because the detector slows down on a long run. The fast preset (keyframes only) took 28.8 s for 5 minutes and 124.6 s for 20. Above 60 minutes was not measured [unverified]. My Mac does about 7.4 s per video minute on the balanced preset.

**When it suggests My Mac.** The panel says "Use My Mac for this one" when the browser cannot decode the video (no WebCodecs, or no HEVC), when WebGPU is missing, when the estimate passes 600 s (10 minutes), or when the video is longer than 60 minutes, the longest run measured under the 4096 MB memory ceiling. For the balanced preset in Chrome the 600 s estimate is reached at a video of about 22 minutes (computed from the `web/src/model/limits.ts` constants); in Safari the scaled constants reach it at about 13 minutes [unverified: Safari figures are Chrome's scaled by 116/61].

**Browser tests.** They drive the installed Chrome through Playwright with synthetic video only (no footage), and are skipped unless enabled:

```
export INFRAME_MODELS=/path/to/models   # the folder that holds onnx/ (made by tools/export_onnx.py)
uv sync --group browser
INFRAME_BROWSER_TESTS=1 uv run --group browser pytest -q tests/browser
```

`INFRAME_SAFARI=1` also opens the real Safari. `tools/browser_limits.py` repeats the limits table above.

Two notes for anyone who redistributes inframe or a build of it, and one for the tracking extra:
- **Tracking extra, GPL.** `trackers` requires `opencv-python`, and its macOS wheel (5.0.0.93, checked in this repo's lock) bundles `libavcodec` built with `--enable-gpl` (libx264, libx265) next to libpostproc, librubberband and libvidstab, which are GPL too. Running it in a child process does not change the license of what is installed. That is why `trackers` is an opt-in extra and not in the default install or the dev group: install it only where GPL-licensed binaries on disk are acceptable, and do not redistribute a build that includes it under Apache-2.0 terms. Tracking is only needed for targets that set `wants_tracks`; `AnyPerson`, motion mode and the fast preset never use it. Decision logged 2026-10-15; replacing `trackers` or the OpenCV wheel is open work.
- Pillow is HPND (permissive, BSD-like), not BSD or MIT.
- The PyAV wheels bundle FFmpeg libraries built as LGPL. Keeping them as separate shared libraries inside the wheel, and not statically linking them into your own binary, keeps that compliant; ship the LGPL notice and offer the FFmpeg source if you redistribute. The `ffmpeg` command used for cutting is the one on the user's PATH, not a bundled copy.


## Saved targets (T2)

A person kept by name, so a later video needs no tap and no photo folder.

```
uv run inframe target add alice --from photos:DIR            # crops, one person per photo
uv run inframe target add alice --from tap:target.json       # the frame of each tap (the video is named in target.json; --video FILE otherwise)
uv run inframe target add alice --from run:OUT/segments.json # a run that kept one person: crops spread over the time they were found
uv run inframe target list | show alice | remove alice
uv run inframe target export alice alice.zip ; uv run inframe target import alice.zip [--name N] [--force]
uv run inframe cut VIDEO --target saved:alice [--add-crops]
```

- **Storage:** `~/Library/Application Support/inframe/targets/NAME/` (`$INFRAME_TARGETS` replaces the folder; `$XDG_DATA_HOME/inframe/targets` off macOS). `target.json`, `crops/cNNNN.jpg` (thumbnails, longest side 512, a person's crop and never a whole frame) and `emb/<embedder version>.npz`. No video is ever stored. The crops are pictures of the person: treat the folder as private.
- **Embedder versions:** the embeddings are keyed by the embedder's version string (`dinov2-small/1`, ...). Another embedder, or a new version of one, embeds the thumbnails again on first use and stores the result next to the old one; `target show` marks versions no embedder uses any more as STALE. A target is **stale in the sense of exit 3** when its thumbnails are missing or unreadable (nothing to embed again): `cut` and `pick` exit 3 and say to add the person again.
- **Adding:** a crop too like one already kept is dropped (embedding dedup), at 32 crops the most redundant one leaves (embedding and clothes colour both count, so a second outfit stays over a tenth crop of the first). A `run:` source must come from a run made with a target (a run of every person or of motion is refused). `cut --target saved:NAME` prints the `target add ... --from run:` command that adds crops of the person the run found; `--add-crops` does it right away. Add crops only from runs you checked: a wrong person in the set lets strangers in.
- **Use:** `saved:NAME` is photo mode with the stored crops as the photos (thresholds, margin and the one-confirm `inframe pick VIDEO --photos saved:NAME` as in "Photo mode and identity"); without a confirm it picks the best track only above the embedder's threshold and margin, else exit 3.
- **Measured** (`uv run python tools/splice.py saved`): a target saved from one composite finds the target in another composite built from different clips of the same target, with no tap.

## Photo mode and identity (T1c)

`inframe cut VIDEO --target photos:DIR` follows the person in the photos of DIR. `inframe pick VIDEO --photos DIR` ranks the tracks of the video against the photos, shows the top 5 as "Is this you?" and writes the confirm into target.json (which names the photos folder, so `--target tap:target.json` is enough). Without a confirm, `cut` takes the best track only when it clears the embedder's threshold and beats every track that shares a frame with it by the margin; otherwise it exits 3 and says which tracks it could not tell apart. `--embedder dinov2` (default), `siglip2` or `color` (no model). `uv sync --extra identity` installs torch and transformers; the models run in a child process, on CoreML when the package can be built (cached in the model cache), else MPS, else CPU. The embedders have honest limits: the thresholds are tuned on synthetic composites. `tools/bench_embed.sh` times the embedders.

`tools/bench_units.sh` (T1e) times the detector on the first 60 s of the regression video (300 frames) for {small, base} x {CPU_ONLY, CPU_AND_GPU, CPU_AND_NE}: ms per frame, model load time, and whether two passes give bit-identical scores; it prints the machine's load average per row, so run it alone on a quiet machine (`bash tools/bench_units.sh`, rows also go to `.logs/bench_units.jsonl`). The default compute units (CPU_AND_GPU since 2026-10-16) were chosen from that table and a repeatability check (speed against repeatability). T1e adds no dependency (license log: no new package; RF-DETR base is Apache-2.0 like small).

Licenses added by T1c (identity extra, opt-in): torch BSD-3-Clause, transformers Apache-2.0, huggingface-hub Apache-2.0, DINOv2-S weights (facebook/dinov2-small) Apache-2.0, SigLIP 2 base weights (google/siglip2-base-patch16-224) Apache-2.0.

`tools/regress.py` follows the default units and compares the regression video with the recorded baseline intervals; an optional `tools/regress_accepted.json` lists the boundaries accepted to move (date, reason, value). Only those boundaries use the new value, and the PASS line prints them.
